1. De qué trata el proyecto

Tándem es una aplicación web para gestionar las monitorías académicas de una universidad. Una monitoría es un acompañamiento donde un estudiante avanzado (el monitor) ayuda a otros estudiantes con una materia.

El problema

Hoy pedir una monitoría depende de grupos de chat y de conocer a alguien. No queda registro de quién atendió a quién ni de qué temas se vieron, y Bienestar Institucional no tiene cifras para tomar decisiones.

La solución

Una sola plataforma donde cuatro perfiles hacen su parte:

PerfilQué hace en el sistema
EstudianteSe registra, pide monitorías, ve a los monitores y su agenda, sigue el estado de sus solicitudes y las cancela.
MonitorPublica los días y horas en que está libre y registra si el estudiante asistió y qué temas se vieron.
DocenteRemite a monitoría a estudiantes de sus materias y consulta el historial de ellos.
Bienestar InstitucionalAsigna monitores a las solicitudes pendientes, genera reportes y administra usuarios y materias.

Objetivos

  • Que un estudiante pueda solicitar monitoría indicando materia, tema y fecha.
  • Que los monitores publiquen su disponibilidad y se les encuentre fácil.
  • Dejar registro de asistencia y temas vistos.
  • Dar a Bienestar la asignación y los reportes filtrables.

3. Cómo ponerlo a funcionar

Requiere Python 3.10 o superior. Desde una terminal, dentro de la carpeta del proyecto:

# 1. Crear y activar el entorno virtual (una "caja" aparte para las librerías)
python -m venv venv
venv\Scripts\activate

# 2. Instalar las dependencias que lista requirements.txt
pip install -r requirements.txt

# 3. Crear el archivo de configuración a partir del ejemplo
copy .env.example .env

# 4. Crear la base de datos con datos de ejemplo
python init_db.py

# 5. Arrancar el servidor
python app.py

Después abre http://127.0.0.1:5000 en el navegador.

5. El patrón MVC explicado con un ejemplo real

MVC separa el programa en tres capas para que cada archivo tenga una sola responsabilidad:

  • Modelo (M): habla con la base de datos. No sabe nada de páginas web.
  • Vista (V): el HTML que ve el usuario. No hace consultas.
  • Controlador (C): recibe la petición, valida, llama al modelo y elige qué vista mostrar.

Ejemplo: el estudiante envía una nueva solicitud

1 · NavegadorEnvía el formulario (POST)
2 · app.pyCarga el usuario y revisa el CSRF
3 · ControladorValida los datos
4 · ModeloINSERT en la base
5 · ControladorMensaje y redirección
6 · VistaPanel con la solicitud nueva
  1. El estudiante llena el formulario de estudiante/solicitud_form.html. El JavaScript de validacion.js revisa los campos antes de enviarlos.
  2. Al llegar el POST a /estudiante/solicitudes/nueva, Flask ejecuta primero cargar_usuario (¿quién es?) y verificar_csrf (¿el token es válido?).
  3. La función nueva() de controllers/estudiante.py está protegida con @rol_requerido("estudiante"): si el usuario no es estudiante, responde 403.
  4. validar_solicitud() (en utils.py) revisa que haya materia, que el tema tenga al menos 4 letras y que la fecha no sea anterior a hoy. Si hay errores, se vuelve a mostrar el formulario con el mensaje debajo de cada campo.
  5. Si todo está bien, se llama a solicitudes.crear(...) en models/solicitud.py, que ejecuta un INSERT con parámetros (?). Así se evita la inyección SQL.
  6. El controlador guarda un mensaje (flash) y redirige a /estudiante/. El panel consulta de nuevo la base y muestra la solicitud con estado Pendiente.
def crear(estudiante_id, materia_id, tema, fecha, notas, remitida_por=None):
    db = get_db()
    cur = db.execute(
        "INSERT INTO solicitudes (estudiante_id, materia_id, tema, fecha_preferida, notas, remitida_por)"
        " VALUES (?, ?, ?, ?, ?, ?)",
        (estudiante_id, materia_id, tema, fecha, notas, remitida_por))
    db.commit()
Redirigir después de un POST evita que, al recargar la página, el navegador reenvíe el formulario y se cree la solicitud dos veces.

6. La base de datos

Es relacional y está definida en schema.sql. Tiene siete tablas:

TablaQué guardaLlaves y reglas
usuariosTodas las personas: nombre, código, correo, contraseña cifrada, rol y programa.PK id. Correo y código únicos. rol solo puede ser estudiante, monitor, docente o bienestar.
materiasMaterias con monitoría.PK id. Nombre único. FK docente_id → usuarios.
inscripcionesQué estudiante cursa qué materia.PK compuesta (estudiante, materia). FK a usuarios y materias.
monitor_materiasQué materias atiende cada monitor.PK compuesta (monitor, materia). FK a usuarios y materias.
disponibilidadesDía y franja horaria libre del monitor.FK monitor_id. El día es de lunes a sábado y la hora de fin debe ser mayor que la de inicio.
solicitudesPedidos de monitoría.FK a estudiante, materia, monitor y docente que remite. estado: pendiente, asignada, atendida o cancelada.
sesionesAsistencia y temas vistos.FK solicitud_id único: una sesión por solicitud.

Cómo se relacionan

usuarios ──< inscripciones >── materias        (muchos a muchos)
usuarios ──< monitor_materias >── materias   (muchos a muchos)
usuarios ──< disponibilidades                (uno a muchos)
usuarios ──< solicitudes >── materias        (estudiante, monitor y docente)
solicitudes ── sesiones                        (uno a uno)

Integridad de datos

  • Llaves foráneas activas: PRAGMA foreign_keys = ON (SQLite no las valida si no se activa). Si se intenta usar una materia que no existe, la base lo rechaza.
  • ON DELETE: al borrar un usuario se borran en cascada sus inscripciones, franjas y solicitudes. Una materia con solicitudes no se puede borrar (RESTRICT), y el sistema avisa en lugar de fallar.
  • CHECK: la base misma impide roles, estados o horarios inválidos, aunque el programa tuviera un error.

Ciclo de vida de una solicitud

PendienteEl estudiante (o el docente) la crea
AsignadaBienestar elige monitor
AtendidaEl monitor registra la sesión
CanceladaEl estudiante desiste
  • Se puede editar solo si está pendiente.
  • Se puede cancelar si está pendiente o asignada.
  • Se puede eliminar si está pendiente o cancelada.

Inyección SQLTodas las consultas usan parámetros ?, nunca se pega texto del usuario dentro del SQL.models/

Redirecciones a páginas externasDespués de ingresar solo se acepta volver a rutas internas.auth.py

8. Qué puede hacer cada perfil

Visitante (sin sesión)

Ve la portada con los monitores disponibles, puede filtrarlos por materia y buscar por nombre. Puede registrarse (solo como estudiante) o ingresar. Monitores, docentes y personal de Bienestar los crea Bienestar.

Estudiante · HU-1 a HU-4

  • Registro e ingreso (HU-1): nombre y apellido, código de 6 a 10 dígitos, correo, programa, contraseña de mínimo 8 caracteres y las materias que cursa.
  • Solicitar (HU-2): elige materia, tema y fecha, con notas opcionales.
  • Ver monitores (HU-3): lista con sus materias y franjas, con filtro y búsqueda.
  • Mis solicitudes (HU-4): tabla con estado, monitor asignado y, cuando ya fue atendida, si asistió y qué se vio. Puede editar, cancelar o eliminar según el estado.

Monitor · HU-5 y HU-6

  • Mi agenda (HU-5): crea, edita y elimina sus franjas (día, hora de inicio y de fin). La hora de fin debe ser posterior a la de inicio.
  • Registrar sesión (HU-6): sobre una solicitud asignada marca si el estudiante asistió y anota los temas vistos. Si asistió, los temas son obligatorios. La solicitud pasa a Atendida y la sesión se puede corregir.

Docente · HU-7 y HU-8

  • Remitir (HU-7): ve solo a los estudiantes inscritos en sus materias y los remite escribiendo el tema. Se crea una solicitud marcada como "remitida por docente". Si alguien intenta remitir a un estudiante de otra materia, el servidor lo rechaza.
  • Historial (HU-8): todas las monitorías de sus estudiantes, con filtro por materia y búsqueda por estudiante o tema.

Bienestar Institucional · HU-9 y HU-10

  • Asignar (HU-9): ve las solicitudes pendientes y elige un monitor. Solo se pueden elegir monitores que atienden esa materia. Debajo hay un resumen por materia.
  • Reportes (HU-10): filtra por materia, monitor y estado, y busca por estudiante o tema. La tabla se actualiza sin recargar.
  • Usuarios: crear, editar y eliminar personas, con su rol y sus materias. No puede eliminar su propia cuenta.
  • Materias: crear, editar y eliminar, asignando el docente.

9. El frontend: diseño, JavaScript y fetch

Diseño

  • Paleta "campus eléctrico": violeta eléctrico como color de marca, azul noche casi negro para los fondos oscuros, amarillo sol para la acción principal, coral y menta como acentos, y papel cálido para leer cómodo. Cada color tiene un papel (por ejemplo, el amarillo es solo para acciones y el estado "pendiente"; la menta, para "asignada"). Están definidos una sola vez como variables CSS en landing.css (--ink, --violet, --sun, --coral, --mint…), así que cambiar la paleta es cambiar un bloque.
  • Tipografía: Fraunces (títulos, con carácter editorial) y DM Sans (texto y formularios).
  • Logo: dos círculos que se superponen (violeta y coral): estudiante y monitor trabajando "en tándem".
  • Pantalla de carga: dura poco más de un segundo y aparece una sola vez por pestaña (carga.js guarda una marca en sessionStorage); en las demás páginas la app responde al instante. Para volver a verla, abre una pestaña nueva o una ventana de incógnito.
  • Pulido de interfaz: los botones reaccionan al presionar, las ventanas y avisos "llegan" con desenfoque y escala suaves y se van por el mismo camino, la barra superior es translúcida, el botón de envío muestra un indicador mientras trabaja y se respetan las preferencias de movimiento, transparencia y contraste reducidos del sistema.
  • Responsive: en pantallas pequeñas las tablas se convierten en tarjetas y el menú se pliega.
  • Accesibilidad: enlace para saltar al contenido, foco visible, etiquetas en cada campo, contraste revisado y respeto a "reducir movimiento".

Animaciones de la portada

Pantalla de carga de poco más de un segundo, texto que se enciende palabra por palabra al leer, cifras que cuentan, perfiles en un carrusel horizontal anclado, una foto que crece hasta ocupar toda la pantalla y tarjetas que se apilan al avanzar. Se hacen con GSAP y ScrollTrigger; Lenis suaviza el scroll. Si el JavaScript falla, la portada sigue siendo legible.

JavaScript propio

ArchivoQué hace
carga.jsControla la pantalla de carga: una vez por sesión, ~1 s.
validacion.jsRevisa cada campo al salir de él y al enviar: obligatorio, correo, patrón (código), longitud mínima, cantidad de palabras, fecha mínima (hoy) y hora de fin posterior a la de inicio. Muestra el error bajo el campo y pide confirmación antes de eliminar o cancelar. También convierte los mensajes de Flask en avisos emergentes.
landing.jsAnimaciones de la portada y el filtro de monitores.
reportes.jsActualiza la tabla de reportes mientras se escribe.

Qué es fetch y dónde se usa

fetch() pide datos al servidor sin recargar la página. Se usa en dos sitios: en la portada, que consulta /api/monitores?materia=1&q=ana, y en los reportes, que consultan /bienestar/api/reportes. El servidor responde JSON (texto estructurado) y JavaScript dibuja las filas.

GET /api/monitores?materia=1
→ [{"nombre":"Camila Rojas","materias":["Cálculo I","Álgebra Lineal"],
    "franjas":["Lunes 14:00 – 16:00","Miércoles 10:00 – 12:00"]}]
Degradación elegante: el formulario de filtros de los reportes funciona también sin JavaScript (envía un GET normal). El JavaScript solo lo hace más cómodo.

10b. La rúbrica técnica y cómo la cumple el proyecto

El profesor evalúa cinco criterios con tres niveles: Excelente (100 %), Aceptable (70 %) e Insuficiente (0 %). Esto es lo que pide el nivel Excelente y dónde se cumple.

CriterioQué pide el nivel ExcelenteCómo se cumple
Campos obligatorios e interfazTodos los formularios marcan los obligatorios con asterisco (*) y no hay errores ortográficos.Cada formulario muestra "* Campo obligatorio" y pone el asterisco rojo en cada etiqueta obligatoria (macros campo y lista en _macros.html). Los textos se revisaron con tildes y ortografía.
Validaciones y feedbackValida en cliente (JS) y servidor (Python), con alertas visuales (Toast, modales o componentes de la interfaz), no con alert().Cliente: validacion.js. Servidor: utils.py. Avisos tipo Toast para éxitos y errores, mensajes bajo cada campo y una ventana de confirmación propia (<dialog>) en lugar de confirm(). Páginas de error 400, 403, 404 y 500 con el diseño de la página; el modo de depuración (el que muestra el Traceback) viene apagado por defecto.
Visualización de datos y paginaciónPaginación funcional e interactiva, con filtros y búsquedas dinámicas que no alteran el diseño.Reportes, Usuarios e Historial del docente paginan de 10 en 10 con LIMIT y OFFSET en SQL (models/), y un COUNT(*) para saber cuántas páginas hay. En Reportes, la tabla, los filtros, el buscador y los botones de página se actualizan con fetch sin recargar y la dirección conserva la página. Los datos de ejemplo traen 25 solicitudes y 14 usuarios para que se vea.
Conexión a BD y persistenciaLos datos del frontend se guardan en la base relacional y se comprueba la persistencia en vivo, de forma inmediata.SQLite relacional; cada formulario ejecuta un INSERT, UPDATE o DELETE con commit inmediato. Se demuestra en vivo y reiniciando el servidor.
Renderizado dinámico (Full Stack)Los datos se consumen del backend y no están escritos a mano en el HTML.Las pantallas se arman con Jinja2 desde la base, y hay endpoints JSON consumidos con fetch: /api/monitores y /bienestar/api/reportes.
Para la sustentación: el criterio de renderizado dinámico dice que el frontend debe consumir datos reales del backend. Las pantallas con formularios usan plantillas del servidor (Jinja2), y las que filtran y paginan datos (monitores en la portada y reportes) usan una API JSON. Puedes decirlo así de claro.

12. Preguntas probables de la sustentación

¿Qué es MVC y dónde está en el proyecto?

Es separar el programa en Modelo (acceso a datos, models/), Vista (HTML, templates/) y Controlador (rutas y reglas, controllers/). Así se puede cambiar una parte sin romper las otras.

¿Por qué SQLite y no MySQL o PostgreSQL?

Los lineamientos aceptan los tres. SQLite no necesita instalar un servidor, lo que hace el proyecto fácil de instalar y de revisar. Es relacional y soporta llaves primarias, foráneas y restricciones. Si el sistema creciera, las consultas SQL se pueden llevar a PostgreSQL con pocos cambios.

¿Cómo se guardan las contraseñas?

No se guardan: se guarda un hash generado con generate_password_hash. Al ingresar, check_password_hash compara la contraseña escrita con el hash. Aunque alguien viera la base, no obtendría las contraseñas.

¿Qué es CSRF y cómo lo evitan?

Es un ataque donde otra página hace que tu navegador envíe un formulario a nuestro sitio aprovechando tu sesión. Cada formulario lleva un token aleatorio que también está en la sesión; si no coinciden, el servidor responde 400.

¿Qué es una inyección SQL y cómo la evitan?

Es cuando el texto del usuario se mezcla con el SQL y cambia su significado. Aquí todas las consultas usan parámetros (?), por lo que el dato nunca se interpreta como código.

¿Por qué validan dos veces?

La validación del navegador mejora la experiencia (avisa al instante), pero cualquiera puede saltársela. La del servidor es la que realmente protege los datos.

¿Cómo controlan quién puede ver cada pantalla?

Con el decorador @rol_requerido, que consulta el rol del usuario en sesión. Además, cada ruta que recibe un identificador verifica que el registro le pertenezca al usuario.

¿Qué hace fetch y por qué lo usan?

Pide datos al servidor sin recargar la página. Lo usan el filtro de monitores y los reportes para dar una búsqueda dinámica.

¿Qué pasa si se borra un usuario o una materia?

Las llaves foráneas lo controlan: al borrar un usuario se borran en cascada sus inscripciones, franjas y solicitudes; una materia con solicitudes no se puede borrar y el sistema lo explica.

¿Qué es un Blueprint?

Un grupo de rutas de Flask. Hay uno por perfil (estudiante, monitor, docente, bienestar…), lo que mantiene el código ordenado.

¿Qué mejoras tendría a futuro?

  • Notificaciones por correo cuando cambia el estado de una solicitud.
  • Calendario con choque de horarios entre solicitudes y franjas.
  • Exportar reportes a Excel o PDF.
  • Migrar a PostgreSQL y desplegar en un servidor.
Honestidad técnica: los datos de ejemplo y las fotos de la portada son de demostración. Las fotos se cargan desde Unsplash; si no hay internet, la portada se ve sin ellas pero el sistema funciona igual.
